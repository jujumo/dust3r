= DUSt3R Docker / Podman setup
:toc:

This directory bundles everything needed to run the DUSt3R demo or open
an interactive training shell inside a container. It works with both
Docker and Podman (auto-detected, Podman preferred). For running the
training on an HPC Slurm cluster there is also an Apptainer-based path
(see _Running on a Slurm cluster_ below).

== Layout

[cols="1,3"]
|===
| `demo.sh`                   | Build (if needed) and launch the Gradio demo via `compose up`.
| `shell.sh`                  | Open an interactive bash shell inside the demo image (for training / manual work).
| `train.sh`                  | Run the CO3D-subset training smoke-test locally in its own container via `compose run`.
| `to_apptainer.sh`           | Repack the already-built container image into an Apptainer `.sif` for the cluster (no rebuild).
| `slurm_train.sh`            | Submit the training to Slurm via `sbatch` + `apptainer exec --nv` (cluster counterpart of `train.sh`).
| `files/train_entrypoint.sh` | Shared entrypoint for `train.sh` AND `slurm_train.sh`: bootstraps prerequisites, then runs `train.py`.
| `files/prepare_co3d.sh`     | Idempotent one-time bootstrap: downloads + preprocesses the CO3D subset and fetches the CroCo v2 checkpoint (both persist on the host).
| `docker-compose-cuda.yml`   | CUDA service definition. Reserves all host GPUs.
| `docker-compose-cpu.yml`    | CPU-only service definition. Same image conventions, no GPU.
| `files/cuda.Dockerfile`     | CUDA image (built on `nvcr.io/nvidia/pytorch:24.01-py3`). Compiles the RoPE CUDA extension at build time.
| `files/cpu.Dockerfile`      | CPU image (built on `python:3.11-slim`).
| `files/demo-entrypoint.sh`  | Container entrypoint for `demo.sh`: downloads the checkpoint into the bind-mounted dir if missing, then launches `demo.py`.
| `files/checkpoints/`        | Host-side checkpoint cache. Bind-mounted at `/dust3r/checkpoints` so weights persist between container runs. Gitignored.
|===

== Two ways to run

=== `demo.sh` — Gradio web UI

[source,bash]
----
bash demo.sh --with-cuda --model_name=DUSt3R_ViTLarge_BaseDecoder_512_dpt
# drop --with-cuda for the CPU image
# --engine=docker|podman forces a specific engine
----

Uses `compose up`. The image has the repo `COPY`'d into it at build time
(so code edits on the host require a rebuild to take effect). Only the
checkpoint directory is bind-mounted. Gradio listens on host port
**37860**.

=== `shell.sh` — interactive shell

[source,bash]
----
bash shell.sh              # CUDA shell
bash shell.sh --cpu        # CPU shell
bash shell.sh --engine=docker
----

Uses `compose run --rm`. Adds:

* `-v $REPO_ROOT:/dust3r` — live host repo overlay, so code edits are picked up without rebuilds.
* `-v /dust3r/croco/models/curope` — anonymous volume that re-masks the curope subdir with the image's contents. Without this, the bind-mount above would hide the in-image-compiled RoPE CUDA `.so` and you'd fall back to the slow PyTorch RoPE (with a warning).
* `--service-ports` — publishes port 37860 from the compose file, so a `demo.py` launched by hand inside the shell is reachable from the host.

The shell starts in `/dust3r` and can be used for training (see
`shell.sh`'s own header comments for a CO3D-subset training quickstart).

=== `train.sh` — CO3D-subset training smoke-test

[source,bash]
----
bash train.sh              # CUDA
bash train.sh --cpu        # CPU image
bash train.sh --engine=docker
----

Uses `compose run --rm` with the host repo bind-mounted, like `shell.sh`.
On the **first** run it auto-fetches the CO3D single-sequence subset
(download + preprocess) and the CroCo v2 checkpoint; both persist on the
host (`data/` and `docker/files/checkpoints/`), so subsequent runs skip the
download and go straight to training. Edit `files/train_entrypoint.sh` on
the host to change the training config (it is bind-mounted, no rebuild
needed).

== Running on a Slurm cluster (Apptainer)

`train.sh` runs locally via compose, which does not fit a Slurm cluster:
compose reserves GPUs with `count: all` (fighting the scheduler) and compute
nodes usually have no container daemon. The cluster path uses **Apptainer**
instead — it is daemonless, runs as your user, and `apptainer exec --nv`
honours the `CUDA_VISIBLE_DEVICES` that Slurm assigns to the job.

Both trainers run the **same** `files/train_entrypoint.sh`, so the training
config (datasets, model, hyperparameters) lives in one place and the local and
cluster runs cannot drift apart.

=== Step 1 — build the `.sif` (once)

[source,bash]
----
# repacks the image you already built with demo.sh / shell.sh — no rebuild
APPTAINER_TMPDIR=/home/$USER/dust3r/apptainer-tmp bash to_apptainer.sh
# --engine=docker|podman, --image=<ref>, --output=<path> override the defaults
----

Produces `files/dust3r.sif`. It needs ~50 GB of scratch (a ~25 GB intermediate
OCI tarball plus the unpack), so point `APPTAINER_TMPDIR` at a roomy filesystem
— **not** `/tmp` — and the script funnels both podman's and apptainer's temp
dirs there. (This EL9 apptainer build lacks the `containers-storage:`
transport, so the podman path stages an OCI tarball rather than reading the
local image store directly; the tarball is removed on exit.)

=== Step 2 — submit the training

[source,bash]
----
bash slurm_train.sh
# override resources via env vars, e.g.:
PARTITION=gpu GPUS=2 TIME=4:00:00 bash slurm_train.sh
----

Defaults: partition `debug` (chaos V100 nodes, 1-day cap), account `ffs-3d`,
1 GPU, 8 CPUs, 48 GB, 12 h walltime. Each is overridable via the env vars
`SIF PARTITION ACCOUNT GPUS CPUS MEM TIME JOBNAME`; set `ACCOUNT=` (empty) to
let Slurm pick the default account. Logs land in
`<repo>/slurm-logs/<jobname>-<jobid>.out`:

[source,bash]
----
tail -f ../slurm-logs/dust3r-train-<jobid>.out
----

Like `train.sh` / `shell.sh`, the live host repo is bind-mounted over `/dust3r`
(code edits are picked up without rebuilding the `.sif`). The compiled RoPE
CUDA extension is preserved the same way compose preserves it: on first run the
script extracts `croco/models/curope` out of the `.sif` into `files/curope/`
and binds it back over the repo mount, so the in-image `.so` is not shadowed by
the source-only host submodule (otherwise you would silently fall back to the
slow PyTorch RoPE). Monitor curves with `tensorboard.sh` pointed at the same
`checkpoints/` output dir (it is on the bind-mounted host repo).

NOTE: `train_entrypoint.sh` runs a single `python train.py`, so it uses one GPU
regardless of `GPUS`. For real multi-GPU training switch that line to
`torchrun --nproc_per_node=$GPUS train.py …` (see the repo-root README
"Our Hyperparameters").

== Why `docker/files/checkpoints/` is mounted separately

The `compose` files declare an explicit volume `./files/checkpoints:/dust3r/checkpoints`.
This is required by `demo.sh`, which does NOT bind-mount the host repo
(the image has the code baked in via `COPY`), so without this volume the
multi-GB downloaded `.pth` would be lost on every `compose down`.

With `shell.sh` the entire host repo is bind-mounted, so this volume is
technically redundant — but it still wins the overlay order and ensures
`/dust3r/checkpoints` always points at the same persistent host directory,
regardless of whether you came in via `demo.sh` or `shell.sh`.

== Caveats

* **Proxy + Gradio**: on a network with an HTTP proxy (e.g. NLE), set
  `NO_PROXY=localhost,127.0.0.1` before launching `demo.py`, or Gradio's
  internal startup probe will be intercepted and fail with HTTP 503.
* **`--local_network`**: by default Gradio binds to `127.0.0.1` inside
  the container, which the host port forward can't reach. Use
  `python3 demo.py --local_network …` to bind `0.0.0.0`.
* **Editing curope sources**: edits to `croco/models/curope/{kernels.cu,curope.cpp}`
  are NOT live inside `shell.sh` (shadowed by the anonymous volume).
  Rebuild the image, or rebuild in-place inside the container:
  `cd croco/models/curope && python setup.py build_ext --inplace`.
* **GPU count**: `docker-compose-cuda.yml` reserves `count: all`. If the
  host has fewer GPUs than your `torchrun --nproc_per_node=N`, you'll
  get `CUDA error: invalid device ordinal`.
